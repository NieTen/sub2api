# OKPay 认证排查

## 已确认的事实

`payment gateway error: OKPay 返回业务失败状态（身份认证失败……）` 表示程序已收到 OKPay 的业务拒绝响应。本站将支付网关失败映射为 HTTP 503，不能由这个 503 推断 OKPay 服务不可访问，也不能仅凭提示认定商户 Token 填错。

已在本机 PHP 7.4.3 环境直接加载提供的 `OkayPay (1).php`，使用假商户凭据执行附件的 `sign`、`checkSign` 以及 `payLink/post` 请求捕获，与 Go 实际生成的表单对照。测试不会向真实商户创建订单。

- 十组正常商户 ID 的签名、签名原文和 PHP 解析后的字段一致，覆盖中文、特殊字符 Token、空值、零值及小数金额。
- PHP 的 `checkSign` 接受 Go 实际发送的测试请求。
- 另一个首尾带空格的 ID 用例存在参数差异：Go 构造器去除 ID 首尾空白，附件 PHP 原样保留。Go 发送值与自身签名仍一致。
- 配置保存链路不会改写非空 Token 的 `+`、`%` 等字符；界面只用去除空白后的值检查是否为空，保存仍使用原值。

这些结果只证明上述输入下的协议兼容，不能代替真实商户认证。当前没有得到真实凭据在同一服务器上的成功、失败对照，因此未把某一个差异认定为生产故障根因，也未盲目修改生产签名算法。

## 请求差异

| 项目 | 当前程序请求 | 附件 PHP 请求 |
| --- | --- | --- |
| 提交格式 | 表单编码 | 表单编码 |
| 签名算法 | 过滤空值、外层排序、解码拼接后 MD5 大写 | 相同 |
| 表单中签名位置 | `sign` 按字段名排序 | `sign` 追加在最后 |
| 波浪号编码 | 保留 `~` | 编码为 `%7E` |
| User-Agent | `Go-http-client/1.1` | `HTTP CLIENT` |
| Accept | `application/json` | `*/*` |

PHP 解析表单后重新排序验签时，字段顺序和波浪号编码不会改变已验证用例的签名。请求头是否影响真实商户认证，需要在相同服务器、相同配置下验证。

## 后台诊断

升级到 `v0.2.11.4`，进入「系统设置 → 支付设置 → 管理服务商」，在已保存的 OKPay 实例上点击「诊断认证」。可以诊断尚未启用的实例，但诊断只使用已保存配置；编辑后需先保存。

服务端一次读取该实例配置，分别以当前程序传输方式和 PHP 示例兼容方式向同一 `/balance` 接口发送一次只读请求，总超时不超过 25 秒。两次请求使用同一组最终商户 ID 和 Token。操作不调用 `payLink` 或 `transfer`，不创建充值订单，也不会自动重试。

诊断只返回认证分类和固定说明，不返回商户余额、Token、签名、请求原文或上游完整响应。可以将页面中的两项状态与结论用于后续排查，无需发送密钥。

| 结果 | 可以确认的范围 | 后续方向 |
| --- | --- | --- |
| 两种方式都认证通过 | 已保存配置在当前服务器可通过只读商户认证 | 对比下单接口专属字段与实际选择的服务商实例；不能直接认定下单正常 |
| 仅 PHP 示例兼容方式通过 | 相同配置、相同服务器上的传输方式影响认证 | 再验证下单请求的兼容差异后修复对应传输 |
| 仅当前方式通过 | 当前程序可通过此只读接口认证 | 不应直接切换成 PHP 传输；继续核对下单请求 |
| 两种方式都被拒绝 | 上游对当前保存配置与服务器环境均拒绝认证 | 核对商户配置与上游访问环境；该结果不能区分凭据问题和访问策略 |
| 无法形成对照 | 存在网络、HTTP 或响应格式异常 | 根据分类先处理异常，再进行认证对照 |

`/balance` 只包含商户 ID 和签名。正常数字 ID 下，两种表单正文相同，主要用于核验已保存凭据及请求头差异；它不能覆盖 `payLink` 中中文名称、金额、返回地址等专属参数。

## 回归验证

仓库中的 PHP 黄金用例保存固定假凭据与原 PHP 计算结果，常规 Go 测试可离线验证。安装 PHP 的环境还可运行 PHP 差分测试；未安装 PHP 时不会因此阻止常规构建。线上认证结果仍以后台诊断和实际商户反馈为准。
